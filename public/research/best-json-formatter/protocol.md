# Which online JSON formatter is best? Study protocol (pre-registered)

Status: **frozen before any measured run.** The git commit that adds this file is the pre-registration. Any change
after the first measured run is listed under "Deviations" at the end, with its date and reason; nothing is edited
silently.

Publisher: Tool Kumar (tools.vikasmaur.com), which makes one of the tested tools. See "Conflict of interest".

## 1. Question

Which free online JSON formatter gives a person the best result when they paste JSON and want it formatted
(pretty-printed)? "Best" is measured with the five things a person can notice: is the output safe, is it fast, does
the data stay private, is it easy to use, and is the page pleasant and accessible.

## 2. Which tools are tested (inclusion rule)

1. **Search snapshot.** On one day, from a GitHub Actions runner in the United States, we record the first results page
   of Google and Bing (English, United States, signed out, no personalization) for five queries:
   `json formatter`, `json beautifier`, `json viewer`, `json validator`, `format json online`.
   That gives 10 lists. The raw pages, screenshots and the parsed lists are published.
   If a search engine shows a CAPTCHA, we retry once from a new runner; if it is still blocked, that engine's lists
   are taken with an ordinary desktop browser the same week, and the article says so.
2. **Organic results only.** Ads, "People also ask", videos, AI summaries and other boxes are ignored. Only the first
   10 organic results on the first page of each list count (fewer if the page shows fewer).
3. **Eligible results** are free web pages where anyone can paste JSON and get formatted JSON text back, with no
   sign-in. Not eligible: articles, Q&A sites, code repositories, package pages, browser-extension or app-store
   listings, and paid-only tools.
4. **One entry per tool.** A site appearing with several pages counts once, with the page that ranked highest for
   `json formatter` (else the highest-ranked eligible page overall).
5. **Order.** Tools are ordered by the number of lists they appear in (most first), then by their best position,
   then by their average position. The first **12** are tested.
6. **Publisher's tool.** Tool Kumar is added as a 13th tool if it is not already among the 12. It is tested and
   scored exactly like the others (see section 9).

## 3. Test environment

- GitHub Actions, `ubuntu-24.04` standard runner (2 vCPU, about 7 GB RAM). The CPU model and memory of every job
  are recorded.
- Playwright `playwright-core` 1.64.1 and the browsers it ships: Chromium (Chrome's open-source base) and Firefox.
  Browsers run **headed** (a real window on a virtual X display, Xvfb), unmodified. We do not disguise automation,
  change the user agent, or block ads.
- Desktop window 1920 × 1080. Phone run: 390 × 844, device scale 3, touch, mobile user agent, CPU slowed 4×.
- Every measured run uses a **new browser profile** (no cache, cookies or storage), i.e. a first visit.
- Each tool is used with its **default settings**. We only change a setting when the formatting function cannot be
  reached without it, and say so.
- A consent or cookie dialog is answered with the most privacy-protective choice offered ("Reject all", "Necessary
  only"), otherwise closed. Its appearance is recorded.
- If a site shows a bot check, we retry once in a later job. A site still blocked is reported as "could not be
  tested automatically" for the affected tests; we never solve or bypass a challenge.
- Order: within each repetition every tool runs once, in a seeded random order, so slow periods on the runner hit
  all tools alike.

## 4. Test data

All test files are generated by `kit/generate.mjs` from a fixed seed, so anyone can recreate them byte for byte and
check them against the published SHA-256 list. Nothing large needs to be downloaded.

- **Speed files**: realistic API-style records (nested objects and arrays, ASCII and non-ASCII text, emoji, escapes,
  integers, decimals, exponents, booleans, nulls; no empty objects or arrays), **minified on one line**, because
  formatting a compact API response is the usual job. Sizes: **100 KB, 1 MB, 10 MB, 50 MB** (decimal, within 0.5%).
  Each file contains a fixed marker string used by the privacy check.
- **Data-safety cases** and **error cases**: small hand-written files in `kit/cases/`, listed below. They can be
  downloaded and pasted into any tool by hand.

## 5. Tests

Each tool has a small adapter file (`kit/adapters/<tool>.mjs`) that only says *where* things are on that page: where
to paste, which control formats, where the result appears, where errors appear, and which controls provide each
feature. The measuring code is shared by all tools. Adapters are published.

The formatting action is always: click into the input, paste with the keyboard shortcut (a real, trusted paste),
then click the tool's format control (skipped for tools that format on paste). If a tool offers several formatting
controls, we use the one labelled Format / Beautify / Pretty print, at the default indentation.

### 5.1 Data safety (Chromium, each case once, retried once only if the harness itself fails)

The formatted output is read in full and tokenized by our lossless reader (numbers kept exactly as written,
strings decoded, duplicate keys and key order kept). It is compared with the input:

| Case | What it checks |
|---|---|
| `big-integer` | `12345678901234567890` stays exactly that |
| `max-safe-plus-one` | `9007199254740993` is not rounded to `…992` |
| `long-decimal` | `0.10000000000000000555111512312578270211815834045` keeps all digits |
| `number-spelling` | `1.0`, `1.50`, `1E+2`, `-0` keep their spelling |
| `huge-exponent` | `1e400` is not turned into `Infinity`, `null` or an error |
| `duplicate-keys` | `{"a":1,"a":2}` keeps both members |
| `key-order` | keys are not reordered |
| `unicode` | emoji, CJK, right-to-left text, combining marks, the U+2028 line separator, a lone surrogate escape |
| `escapes` | `\" \\ \/ \b \f \n \r \t \u0000` keep their meaning |
| `proto-key` | a `"__proto__"` key and an empty key `""` survive |
| `top-level-scalar` | the documents `"text"`, `42` and `null` are accepted (they are valid JSON) |
| `deep-nesting` | 2,000 nested arrays format, or are refused with a clear message, without freezing the tab |
| `long-string` | a single 1,000,000-character string value is kept intact |

Grades: **pass** (same tokens) = 1; **spelling changed** (same exact numeric value, different spelling, e.g.
`1.0` → `1`) = 0.5; **refused with a clear message** (only for `deep-nesting`) = 0.5; **changed data, rejected valid
JSON, crash, or no output within 30 s** = 0. Re-escaping a string (e.g. `é` ↔ `é`) is not a change.

### 5.2 Error help (Chromium, each case once)

Each file is a pretty-printed document of about 15 lines with one mistake on a known line:

| Case | Mistake | Accepted lines |
|---|---|---|
| `trailing-comma` | comma before `}` | the comma's line or the `}` line |
| `missing-comma` | two members without a comma | the line of either member |
| `single-quotes` | `'text'` string | its line |
| `unquoted-key` | `name: 1` | its line |
| `comment` | `// note` line | its line |
| `unclosed-array` | `]` missing at the end | the opening `[` line, the last line, or one past it |
| `bad-literal` | `True` | its line |
| `raw-newline` | an unescaped line break inside a string | the string's first or second line |
| `extra-bracket` | an extra `}` at the end | its line |

Per case: **detected** (the tool says the input is invalid, or says it repaired it) = 0.5; **right line** (the
message names an accepted line, or the editor marks an accepted line) = 0.5. Silently "fixing" the input without
telling the user counts as not detected.

### 5.3 Speed (Chromium 5 runs, Firefox 3 runs, per size)

Per run: open the tool in a new profile, wait for the page to load and settle (network quiet for 2 s, at most
15 s), put the speed file on the clipboard (outside the timing), then time **from the paste key press to the moment
the complete formatted result is in the output and the next frame has been painted**. How "complete" is detected
for each tool is written in its adapter (for example the editor's line count reaching the expected count). After the
run, the full output is read and checked against the input (same tokens); a wrong or partial output is a failure.

Also recorded: the **longest freeze**, the longest gap between two painted frames during the timed period, and
the peak JavaScript memory (Chromium only, informational).

Time limits: 100 KB 30 s, 1 MB 60 s, 10 MB 120 s, 50 MB 120 s. Over the limit, a crashed tab, an error or a size
limit message is a **failure**.

Ladder: sizes run from small to large. A failed run is retried once. If both fail, the remaining runs of that size
and all larger sizes are skipped for that tool and browser and count as failures.

Tools that send the pasted JSON to a server (detected in their 100 KB runs, section 5.4) get **one** run each at
10 MB and 50 MB per browser instead of 5 or 3, so we don't push large files to someone else's server repeatedly.

The value used is the **median over all runs of a size, with failures counted as infinitely slow**.

### 5.4 Privacy (all speed runs, plus the page runs)

- **Does your JSON leave the browser?** Every request URL, request body and WebSocket message sent from the paste
  until 5 s after the result is searched for the marker (raw, URL-encoded, base64, base64url). A request body larger
  than half of the pasted text also counts. One positive in any run marks the tool as "sends your JSON".
- **Third-party hosts**: distinct registrable domains other than the tool's own that the page contacts from
  opening it to 5 s after formatting (median of the page runs).
- **Works offline**: after a normal first visit, the network is switched off and the page reloaded. Pass if it loads
  and formats the 100 KB file correctly.

### 5.5 Page experience (Chromium, 3 runs, 1 MB file)

Largest Contentful Paint of the first visit; bytes transferred until 5 s after formatting; cumulative layout shift
until then; ads (requests to the ad-serving domains in `kit/lib/ad-domains.mjs`, or visible ad iframes);
interruptions (any modal, consent wall, pop-up window or new tab that appears, in any run).

### 5.6 Phone (Chromium phone emulation, 3 runs, 100 KB file)

Pass "works" if the 100 KB file formats correctly. Pass "fits" if the page has no horizontal scroll and the format
control can be reached without zooming.

### 5.7 Other browsers

Firefox: from the speed runs (100 KB and 1 MB both handled). WebKit (Safari's engine, Linux build): one run of the
100 KB file and the `big-integer` and `unicode` cases; pass if all are correct. Real Safari on macOS is not part of
the scored study (macOS runners cost about 10× and would not fit the budget); if budget remains, a small unscored
Safari check is reported separately.

### 5.8 Keyboard and screen readers (Chromium)

- The input has an accessible name (label, `aria-label` or `aria-labelledby`).
- The format control has an accessible name.
- Keyboard only: from the top of the page, Tab (at most 40 presses) reaches the input; after pasting, the format
  control can be reached with Tab (Escape first is allowed for editors that keep Tab) and activated with Enter or
  Space, or the tool has a visible keyboard shortcut for formatting. Pass if the output is formatted.

### 5.9 Features (presence, verified on test day)

Each feature counts only if the adapter names the control or shortcut and the run finds it working or visible on
test day: indentation choice; minify / compact; collapsible tree view; search; sort keys; one-click copy; download
as a file; open a local file; load from a URL; dark mode; repair invalid JSON; convert to another format (CSV, YAML
or XML). Paid-only features don't count. A missed feature reported to us is checked and corrected under
"Deviations".

## 6. Scoring (100 points)

`logScore(x, good, bad)` = 1 at or better than `good`, 0 at or worse than `bad`, and in between
`(ln bad − ln x) / (ln bad − ln good)`. Times in seconds.

| Category | Points | How |
|---|---|---|
| **Data safety** | 25 | 13 cases, equal share of 25, graded as in 5.1 |
| **Speed and big files** | 25 | Chromium medians. 100 KB: 5 × logScore(t, 0.2, 3). 1 MB: 5 × logScore(t, 0.5, 5). 10 MB: 5 × logScore(t, 2, 120). 50 MB: 5 × logScore(t, 5, 120). Longest freeze at 1 MB and at 10 MB: 2.5 × logScore(freeze, 0.1, 3) each (failure = 0) |
| **Privacy** | 20 | JSON stays in the browser: 12. Third-party hosts n: 5 × max(0, 1 − ln(1 + n) / ln 31). Works offline: 3 |
| **Ease of use** | 20 | Error help (5.2): 10. Features (5.9): 0.5 each, 6. Phone works 1, fits 1. Firefox works 1, WebKit works 1 |
| **Page and accessibility** | 10 | LCP: 3 × logScore(lcp, 1, 6). Page weight: 2 × logScore(MB, 0.5, 10). No ads: 1. No interruptions: 1. CLS ≤ 0.1: 1 (≤ 0.25: 0.5). Accessibility (5.8): input named 0.5, control named 0.5, keyboard flow 1 |

Overall rank: by total points, rounded to one decimal. Tools within **1.0 point** of each other share a rank.

**Sensitivity check** (decided now, reported in full): category weights are also re-scaled to these sets, and each
tool's rank under each is published:

| Set | Data safety | Speed | Privacy | Ease of use | Page & a11y |
|---|---|---|---|---|---|
| Default | 25 | 25 | 20 | 20 | 10 |
| Equal | 20 | 20 | 20 | 20 | 20 |
| Features first | 15 | 15 | 15 | 40 | 15 |
| Speed first | 15 | 40 | 15 | 15 | 15 |
| Privacy first | 15 | 15 | 40 | 15 | 15 |

## 7. What this study does not measure

Paid plans, signed-in features, browser extensions, desktop apps and command-line tools; JSON Schema validation;
real Safari, Edge on Windows and real phones (emulated only); other locations than the US runner; editing large
documents after formatting. Results are one week's snapshot of live websites, which change.

## 8. Budget and politeness

All measured runs happen on GitHub Actions within a 500-minute budget. Each site sees about 100 page loads in total,
one at a time. Large files are sent at most once per browser to tools that upload JSON (5.3).

## 9. Conflict of interest

The study is published by Tool Kumar, which makes one of the tested tools. To keep that from shaping the result:

- This protocol, including the scoring, was committed before any measurement.
- Tool Kumar's adapter uses only its public page, like every other adapter.
- No Tool Kumar release is deployed between the first and last measured run; its production build ID is recorded
  before and after. If it changes, all Tool Kumar runs are repeated.
- The ranking is published whatever Tool Kumar's place is, with all raw data.

## 10. Replication

Everything needed is in `kit/`: the generator, the cases, the adapters, the harness, the scorer and the GitHub
Actions workflow. `kit/README.md` explains how to rerun one tool on a laptop or the whole study on GitHub Actions.
